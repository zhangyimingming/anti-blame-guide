# 项目管理与责任分工

## 任务开始前

每项重要工作应尽量明确：

| 字段 | 说明 |
| --- | --- |
| 任务目标 | 要解决什么问题 |
| 负责人 | 对最终结果承担协调或管理职责的人 |
| 执行人 | 实际开展工作的人 |
| 配合方 | 提供接口、数据、资源或专业支持的人 |
| 验收人 | 确认交付是否符合要求的人 |
| 截止时间 | 计划完成时间及关键里程碑 |
| 依赖条件 | 资料、权限、接口、预算或审批 |
| 风险 | 可能影响交付的因素 |
| 记录位置 | 需求、决策、测试和交付材料存放位置 |

角色名称应根据组织实际制度定义；一张表本身不能代替正式授权。

## 需求变更管理

每次重要变更应记录：

1. 变更前后要求
2. 提出人、评估人和确认人
3. 变更原因及优先级
4. 对工期、成本、测试、质量和安全的影响
5. 需要调整的交付计划
6. 最终决定和决定时间

当范围增加但截止时间不变时，提供选择，而不是只说“做不了”：

- 维持期限，缩减或调整范围
- 保持范围，调整期限
- 增加资源，但评估协作与质量风险
- 分阶段交付，将非关键功能移至后续版本

方案应由具备相应权限的负责人确认。

## 风险登记

每项风险至少包含：

- 风险描述与事实依据
- 发生概率和影响程度（如组织采用此评估方式）
- 风险负责人
- 缓解措施和应急方案
- 需要作出的决定
- 下一次检查时间
- 当前状态和关闭依据

## 项目状态报告建议

使用统一结构：

- **已完成**：可验证的交付成果
- **进行中**：当前进度及剩余工作
- **风险与阻塞**：影响、依据、责任人和解决期限
- **待决策事项**：需要谁在何时确认什么
- **计划调整**：变化原因及影响

不要把预计完成说成已经完成，也不要将尚未验证的推测写成确定结论。

## 上线前检查

按项目实际适用的制度检查：

- [ ] 需求范围和版本已确认
- [ ] 测试结果及遗留问题已记录
- [ ] 必要审批已完成
- [ ] 权限、操作人员和执行窗口已确认
- [ ] 备份及恢复安排已准备并按要求验证
- [ ] 监控、告警和应急联系人已明确
- [ ] 验证步骤、回滚条件和停止标准已确定
- [ ] 上线后业务验证和责任交接已安排

清单不是安全保证；高风险变更应遵循组织规定的审查和审批流程。
